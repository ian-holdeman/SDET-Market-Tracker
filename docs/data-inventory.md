# Application data inventory

Reviewed 2026-09-08 against the current local source, installed Supabase Auth SDK, and a fresh anonymous Chromium session. This is an inventory of identified data handling, not a completed security audit or a declaration of legal compliance. No signed-in account contents, tokens, database records or secrets were extracted. The privacy implementation subsequently added local fonts, app-specific Auth cleanup and response headers; see the domain guide for controls and verification boundaries.

Owner policy: public market browsing plus optional sign-in and private watchlists. No analytics, advertising, subscriptions, behavioral profiling or secondary use of personal information. Privacy/deletion contact: ianrholdeman@gmail.com. See [scope and owner direction](privacy-security.md).

## Sign-in, accounts and private watchlists

| Data / operation | Recipient and purpose | Persistence and deletion |
| --- | --- | --- |
| Google identity and consent | Browser redirects through configured Supabase Auth and Google after the user selects sign-in. The app calls signInWithOAuth without additional scopes. Standard Google sign-in uses identity/email/profile scopes; exact production consent configuration must be checked separately. | Supabase owns Auth identities, sessions and associated metadata. The application never asks for a Google password. Account deletion does not delete the Google account or guarantee removal of Google's own records. |
| Auth UUID and profile metadata | Supabase issues the app session. `loadProfile` reads UUID and full_name for the signed-in display and obtains the user's watchlist/admin result. Email and other provider metadata may still exist in the Auth user/session even though the app does not use email for marketing or duplicate it in a public profile table. | [authService.ts](../src/services/authService.ts), [AuthContext.tsx](../src/context/AuthContext.tsx). The installed SDK persists the received session including its user object. Actual optional fields must be verified with synthetic/disposable evidence, not by dumping real user records. |
| Private watchlist | Browser sends Auth credentials, UUID and symbol reads/inserts/deletes directly to Supabase. | `public.watchlist_items` contains only user_id and symbol, with a composite key; there is no app-defined add-time or activity-history column. Items remain until removal or account deletion. Grants/RLS enforce ownership. See [migration](../supabase/migrations/20260907000100_market_authorization.sql) and [account guide](../supabase/README.md). |
| Admin assignment | `private.admin_users` stores an assigned Auth UUID; the client receives a boolean through current_user_is_admin. | Persists until trusted revocation/account deletion. Ordinary app admins cannot read other watchlists. Database owners and privileged operations are a separate access boundary; do not promise the operator has no infrastructure-level access. |
| Registering an unknown asset for a watchlist | Browser sends a bearer token and symbol to `/api/assets/register`; Express verifies the user with Supabase, validates the symbol with Yahoo, then inserts shared asset identity. | [assets.ts](../server/assets.ts). Shared `assets` stores only symbol, not who registered it. It remains after account deletion so other watchlists can reference it. It is not a private watchlist entry or a history of who searched. |
| Registration abuse guard | Server memory temporarily associates verified UUID with attempt count and an expiry timestamp. | Ten-attempt/minute guard, bounded to 1,000 account entries. Expired entries are removed on subsequent verified registration traffic; idle entries can remain until process exit. This is necessary operational processing, not anonymous or literal immediate deletion after one minute. It is not cleared by account deletion. |
| Account deletion | Browser sends a bearer token to DELETE `/api/account`; the server verifies it, derives the UUID and calls Supabase Auth admin hard deletion. | [account.ts](../server/account.ts). Watchlist/admin rows cascade from Auth deletion; shared assets/curation remain. Success triggers browser session cleanup. Uncertain failures retain an error rather than claiming deletion. No code erases provider logs, host backups, mailbox messages or other devices' browser histories. |

Primary provider context: [Supabase Google sign-in](https://supabase.com/docs/guides/auth/social-login/auth-google) specifies identity/email/profile scopes. [Supabase Auth audit logs](https://supabase.com/docs/guides/auth/audit-logs) describes authentication-event logs including identity, time, action, IP/user-agent and metadata. These are provider capabilities, not a verified inventory of the eventual hosted project's enabled settings or retention. The local `analytics.enabled = false` in [config.toml](../supabase/config.toml) is not evidence that all Auth/service logs cease to exist.

## Server requests, caches and logs

- **Yahoo:** [market.ts](../server/market.ts) sends ticker symbols, timeframes and search text to query1/query2.finance.yahoo.com. The server does not forward the browser's bearer token, UUID, cookies or IP headers to Yahoo; Yahoo sees the server-side connection and requested financial query. The app server still receives the original browser request. Search text is user-supplied, so it could contain personal information someone types. There is no persistent search-history table. The shared in-memory cache retains uppercase query keys/results; its 60-second search TTL is freshness, not a deletion promise. Other market caches are documented in [market-data.md](market-data.md).
- **Supabase:** the browser uses the public API key and user session; privileged server registration/deletion uses server-only credentials with session persistence disabled. Service/platform logs and backups have retention separate from live application tables. No hosted retention configuration has been verified.
- **GitHub test evidence:** server requests use an owner-configured credential, repository and run identifiers, not visitors' Auth sessions. Public output contains sanitized test metadata/outcomes, not visitor behavior. [Telemetry contract](../src/telemetry/contract.ts) excludes stdout, error contents and attachments. [Workflow](../.github/workflows/playwright.yml) retains sanitized artifacts for 90 days; this is not a personal-account retention period.
- **Private test snapshots:** [test-snapshot.ts](../server/test-snapshot.ts) stores validated test feeds under a private snapshot directory, not public client assets. Snapshots older than 90 days are rejected on read, but that does not physically delete the file. These are project test results, not sign-in/watchlist records. Other local `.telemetry` files and Playwright reports are development artifacts; no visitor-triggered recording exists. Public demonstration videos are pre-recorded fixtures, documented in [recordings](test-recordings.md).
- **Application logs:** no custom per-visitor access logger or analytics/error-reporting service was found. Code logs startup/configuration failures, market request failures (sometimes with symbol/error objects) and snapshot persistence failures to local console/stdout/stderr. JSON parser failures now receive generic uncached responses through [security middleware](../server/security.ts). Future host/CDN/database logs must be reviewed separately; their existence/retention cannot be excluded from this code scan. Never enable session debug output or preserve Authorization headers in diagnostics.

## User-initiated departures and contact

Google Finance links send an asset identifier, or a Google search restricted to Finance pages with symbol/name/exchange, when followed. They use noopener/noreferrer. The Logic's GitHub source links and Tests run links also navigate to external services; the global no-referrer response header also suppresses referring URLs. Destination services can still receive network metadata and their own cookies. These are not background analytics integrations.

The Contact modal opens a mailto link or copies the owner's email address; it does not submit an in-app contact form. If a visitor emails ianrholdeman@gmail.com, sender address, message, attachments and email metadata reach the owner's Gmail mailbox and the sender's mail provider. The [privacy request procedure](privacy-security.md#privacy-requests-and-retention-procedure) defines proportionate verification and purpose-limited correspondence handling; a fixed mailbox retention duration remains open. The local resume link and demonstration assets are same-origin downloads, not visitor-upload features. No brokerage linking, balances, payment details or transaction imports were found in the reviewed app.
