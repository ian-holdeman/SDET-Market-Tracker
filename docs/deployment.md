## Runtime and load

The deployed service uses request-based CPU, one vCPU, 1 GiB memory, concurrency 16, **service-level** minimum 0 and maximum 2, 30-second request timeout, and startup CPU boost. `/api/health` is a startup/application check; provider outages must not trigger restart loops. Startup rejects mismatched public/server configuration or missing secrets/buckets before listening.

Cold starts are accepted. Snapshot initialization, refresh and conditional persistence stay inside active requests; setting minimum instances above zero would not by itself supply background CPU. SIGTERM stops acceptance and gives active work an eight-second drain deadline. Forced termination or client/network loss can leave completion uncertain; atomic writes preserve the last valid stored generation, but do not guarantee an interrupted operation committed.

A local Linux container under one CPU/1 GiB successfully served the full catalog request and sixteen concurrent coalesced one-year chart requests. The measured cgroup peak was about 55 MiB for that bounded exercise. This supports initial headroom, not a worst-case or hosted latency claim. Market bodies are bounded before parsing; requests have deadlines, in-process work/cache bounds and coalescing. Registration additionally uses a shared database budget. Public market limits remain per process, not global abuse protection. Maximum instances is not an absolute bill cap and can be exceeded transiently; overlapping revisions and external-service charges remain relevant.

## Rollback, recovery and rotation

- Before each deployment, privately record current revision, image digest, commit, manifest, schema versions and secret versions. Keep `current` and `rollback` image tags. Route traffic back with `gcloud run services update-traffic sdet-market-tracker --to-revisions=PREVIOUS_REVISION=100 --project=sdet-market-tracker --region=us-west1`; recheck the service-level maximum and runtime configuration. First-launch rollback can remove public invocation while retaining the database/archive for investigation.
- Prefer additive, backward-compatible migrations. The registration budget migration adds a table/function; the preceding revision does not require their removal. Do not reverse schema changes by dropping user data. Rehearse a restore into an isolated target before using it for production recovery.
- Supabase Free requires owner-managed exports. Before migrations and material curation changes, export schema/roles/data using the provider's current backup procedure to encrypted owner-controlled storage. Keep a current and previous verified backup and record the time window of possible loss. Auth/provider configuration, secrets and archive state require separate recovery records; a database dump alone is not a full application backup. Never use a hosted reset to test restoration.
- On pause recovery, restore/unpause the existing project where supported, verify migrations, Auth URLs and keys, then test sign-in and watchlist isolation. After a replacement project, update both public build and server configuration together. Do not silently reuse a local database or fixture users.
- Rotate the GitHub token with Actions-read access only to this repository. Add a Secret Manager version, deploy and verify history/archive retrieval, retain the previous version through rollback, then revoke it. Rotate Supabase server secrets similarly and recheck trusted operations. Public-key rotation also requires a new client build. Revoke compromised credentials promptly even if that temporarily prevents rollback.
- Archive publication/revocation/recovery follows [pipeline replay](pipeline-replay.md). Never expire the last usable archive through bucket lifecycle. Snapshot loss is recoverable from upstream only while upstream evidence remains available; an archive is a separate historical publication and cannot refill rolling metrics.
